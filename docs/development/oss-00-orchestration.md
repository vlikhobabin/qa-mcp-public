# Оркестрация дорожной карты OSS-00

Согласованный процесс от 2026-09-10. Одна главная Codex-сессия управляет очередью
qa-mcp и последовательно запускает существующий ChangeRail runner. Runner сам
создаёт Codex-сессии реализации, исправления и независимого review. Нового
движка оркестрации или доработки ChangeRail для этого процесса нет.

Стартовый [промпт](prompts/oss-00-orchestrator.md) предназначен для новой сессии.
Правила дополняют [native delivery](native-openspec-delivery.md),
[политику тестов](test-policy.md) и `AGENTS.md`.

## Ответственность и границы

| Участник | Ответственность |
| --- | --- |
| Оркестратор | Выбор следующей доступной карточки, актуализация плана, допуск, запуск runner, проверка результата, обновление roadmap и очереди |
| ChangeRail runner | Статусы исполняемой карточки, этапы реализации, evidence, независимое review, sync/archive, финальные проверки, commit и push |
| Подчинённая сессия мелкого фикса | Один явно ограниченный исправляемый дефект и адресные проверки; отчёт родителю, без самостоятельного commit/push |

В общем checkout работает только один исполнитель, меняющий файлы. Пока runner
или отдельный fix-worker активен, оркестратор читает результаты и сообщает статус,
но не редактирует payload, карточки, профиль, индекс или очередь. Запуск второго
writer запрещён. Не запускайте дополнительный Codex-manager поверх `chrl-run`:
этот runner уже создаёт необходимые дочерние сессии.

Обычная продуктовая доставка с commit/push разрешается стартовым поручением
оркестратору; не запрашивать одно и то же согласование на каждую карточку.
Работы ChangeRail, остановленные FIX-02/I13 и другие frozen records не становятся
разрешёнными из-за общего поручения. Пилот, live 1С, изменение бизнес-данных,
развёртывание и публикация релиза требуют применимой конкретной authority.

## Начало и выбор карточки

1. Проверить `main`, чистый index/worktree, upstream и отсутствие другого writer.
   Сверить локальный HEAD с `origin/main`; при необходимости получить состояние
   remote. Допустим fast-forward чистой ветки; неизвестное расхождение не решать
   принудительным push/reset. Игнорируемые evidence и сессии сохраняются.
2. Прочитать актуальные OSS-00, board и `.changerail/history.json`. Наличие файла
   в `3.inprogress` не означает живой запуск: пять исходных frozen records имеют
   явную disposition. Однако новый незавершённый run нельзя объявить историей.
3. Выбрать минимальный Order Index среди релевантных доступных продуктовых
   карточек с реально завершёнными зависимостями. Не использовать агрегаты,
   canceled и superseded карточки как runner input. `archived`, старый GO и
   сохранённый код не равны завершённой зависимости.
4. Перепроверить проблему на текущем коде. Удалить устаревшие требования и
   дублирующую работу из ещё не принятого плана, сохраняя контракт продукта.
   Уточнить acceptance, зависимости, ограничения, evidence и стоимость тестов.
   Если результат уже доказан другим завершённым изменением, отразить это на
   доске с основанием; не создавать фиктивную реализацию и review.

Начальный выбор — OSS-FIX-04A (`406.231`, P1, без зависимостей). Один change
`oss-fix-04a-isolate-display-host-settings` уже подготовлен; dry-run допуска
прошёл. FIX-02 остановлена, FIX-03 зависит от неё. Исполнение независимых карточек
не снимает этот блокер для последующей квалификации и закрытия эпика.

## Подготовка и доставка одной карточки

1. Для новой исполняемой карточки подготовить `openspec-v1`, один change и
   полный набор proposal/design/delta specs/tasks через `./bin/openspec`.
   Каждому acceptance ID соответствует typed evidence; группы tasks являются
   checkpoint. Использовать текущую политику адресных тестов даже если старый
   draft требовал полный pytest на каждую карточку.
2. Проверить change и выполнить `./bin/chrl native-accept <backlog-card> --dry-run`,
   затем обычный `native-accept`. Он перемещает карточку и может обновить ссылки.
   Проверить и отдельным planning commit зафиксировать и отправить **все точные
   изменения допуска и плана**, включая обновлённые ссылки. Иначе `doctor`
   остановится на грязном дереве. Сам допуск не выполняет commit/push.
3. После допуска не переписывать принятый план. Изменившийся acceptance требует
   явной reconciliation поддерживаемым маршрутом, не правки receipt вручную.
4. Из чистой `main` выполнить `./bin/chrl doctor <todo-card>`, затем
   `./bin/chrl-run <todo-card>`. Сохранить путь run, PID/сессию запуска и вывод
   под `.runtime/qa-roadmap/oss-00/`. Не оставлять запуск без наблюдения; не
   считать истечение времени провалом и не создавать конкурирующий повтор.
5. Дождаться завершения и проверить результат по следующему разделу. Не
   вмешиваться в внутренние этапы runner и не создавать сторонний review-цикл.

## Проверяемый результат и обновление очереди

Одного сообщения worker «готово» или нулевого exit code недостаточно. Проверить:

- карточка перешла в `4.done`, acceptance и Result соответствуют фактическому diff;
- `chrl status <run-dir>`, финальный review и evidence относятся к этому run;
- `publication.json` содержит `state=pushed` и фактический commit; upstream
  содержит этот commit, а дерево чистое;
- выбранные тесты действительно выполнялись; количество, длительность и
  offline/integration/runtime результаты не перепутаны;
- ограничения и незавершённая native квалификация не объявлены закрытыми.

После успешной доставки обновить **текущие** Snapshot/Result/Next/Log OSS-00:
карточка, commit, краткий продуктовый результат, проверенные поверхности,
остаточные ограничения, следующий выбор и причины пропуска заблокированных
карточек. Затем актуализировать следующую карточку на новом коде. Эти изменения
относятся к отдельному planning checkpoint, не к уже замороженному payload
предыдущего runner. Сохранить исторические записи и frozen карточки.

Рабочая заметка `.runtime/qa-roadmap/oss-00/state.json` может хранить HEAD,
текущую/следующую карточку, run-dir, child session ID, PID, фазу, последний
результат и blockers. Это удобство восстановления, не источник статусов или
доказательство GO. Истина — Git, доска и проверяемые receipts. Не публиковать
auth, трассы, сырые логи и локальные runtime-данные.

## Мелкие исправления и дополнительные карточки

Ошибка в acceptance **активной** карточки исправляется её runner в рамках
текущего repair/review процесса. Нельзя объявить её «мелким фиксом» и запустить
параллельного writer или обойти исчерпанный review allowance.

Вне активного/frozen run мелкий фикс допустим без карточки, если у него один
локальный понятный результат, нет нового публичного контракта, изменения
authority/ownership, protocol semantics, миграции данных или live воздействия.
Оценивать по смыслу и риску, а не только по LOC. Оркестратор:

1. Записывает в ignored prompt проблему, воспроизведение, точные разрешённые
   пути, ожидаемый результат, focused checks и запрет расширять scope/публиковать.
2. Запускает свежую сессию, дожидается её завершения и сохраняет JSONL, итоговый
   ответ, exit code, время и идентификатор сессии. Не использовать `resume --last`.
3. Проверяет diff и evidence. При успехе делает scoped commit/push и запись в
   Log OSS-00 с основанием «малый фикс без карточки». Если обнаружен больший
   scope, сохраняет попытку и планирует отдельную карточку, не расширяя молча.

Пример из корня репозитория после подготовки каталога и prompt-файла:

```sh
./bin/codex exec --model gpt-5.6-terra \
  -c 'model_reasoning_effort="high"' --json \
  --output-last-message .runtime/qa-roadmap/oss-00/fix-001/result.md - \
  < .runtime/qa-roadmap/oss-00/fix-001/prompt.md \
  > .runtime/qa-roadmap/oss-00/fix-001/events.jsonl \
  2> .runtime/qa-roadmap/oss-00/fix-001/stderr.log
```

Модели реализации/review обычных карточек задаёт `.changerail/profile.toml`;
пример малого фикса соответствует текущей роли реализации. Флаги CLI проверены
локально; назначение `exec`/JSONL описано в
[официальной документации Codex](https://learn.chatgpt.com/docs/developer-commands#codex-exec).

Для крупного изменения создать дополнительную backlog-карточку с причиной,
acceptance, зависимостями и одним native change. Поставить перед заблокированным
потребителем либо позже, если изменение не мешает текущему пути. Не использовать
новую карточку, чтобы автоматически легализовать незавершённый frozen payload.

## Ошибки, прерывания и предел завершения

При сбое сохранить команду, exit code, последнюю фазу, session/run ID, реальные
времена и dirty diff. Определить, завершился ли процесс, прежде чем продолжать.
Для поддерживаемого нового native run использовать только `chrl resume <run-dir>`
с точным predecessor. Не удалять lock у живого процесса, не обнулять receipts,
не создавать третий review и не перезапускать доставку с нуля.

Ошибка установленного ChangeRail — blocker его источника: сохранить диагностику
и описать требуемое исправление владельцу, но не править/тестировать tooling
в qa-mcp. Внешние сообщения и установка новой версии требуют своего поручения.
Если frozen run блокирует единственного writer, можно продолжать независимое
планирование, но нельзя начинать следующую доставку поверх его dirty payload.

Полный pytest — только при закрытии эпика либо по явному соглашению. Live Linux
и live Windows выполняются отдельно с target, intent, preflight, началом/концом,
результатом и cleanup. Отсутствие такого разрешения не превращать в успешный skip.

Продолжать все доступные согласованные работы. Если остаются только зависимости
остановленной FIX-02, runtime authority или иной реальный blocker, представить
конкретный остаток и решение, требуемое от оператора. Не объявлять OSS-00 закрытой
без её acceptance и эпик-проверки; не обходить блокеры ради формального завершения.

## Дополнение оператора от 2026-09-10 после FIX-04B

Оператор поручил завершить оставшиеся актуальные карточки OSS-00 автономно,
решая возникающие вопросы реализации без повторных запросов. Подготовленное
ручное завершение FIX-04B прямо разрешено; его отдельный журнал сохраняет
native-остановку, NO-GO и оба независимых review. При необходимом локальном
исключении фиксировать конкретную причину, принятое решение и фактические
доказательства; не выдавать ручной путь за успешный native resume. Доработка
ChangeRail и возобновление отменённых maintenance-карточек в поручение не входят.

Следующий остаток FIX-02 — финальное доказательство C3 и применимость ранее
полученного GO к текущему продукту. Незавершённый старый прогон сохраняется;
используется текущая политика адресных тестов. Учёт двух review не обнуляется,
исторические файлы и неподтверждённые зависимости не объявляются завершёнными.

Урок планирования FIX-04B: задачи checkpoint описывают реализацию и подготовку
доказательств. Aggregate sync/handoff, archive и публикация остаются требованиями
последующих стадий runner, без checkbox внутри предшествующих групп. Иначе
возникает цикл «завершить финализацию до допуска к финализации».

## Дополнение после доставки FIX-03

FIX-02 завершена и опубликована в `289f432`; FIX-03 — штатным runner в `f5ad9c0`.
Их прежние остановки и review сохранены. Неблокирующий R4 после GO уточнён
отдельным test-only исправлением `1046b9f`; оно не создаёт новый независимый
review и не меняет исходный verdict. Текущий выбор — FIX-04C.

Для typed proof сохранять terminal node results через `pytest -v`. Сам по себе
нулевой код краткого pytest не заменяет наблюдения каждого acceptance. После
Result/Log, semantic sync и archive fingerprint меняется: соответствующая
финализирующая сессия обновляет current proof и завершает handoff, а не выходит
с отчётом о missing/stale receipts. Это уже разрешённая работа финализации.
В поддерживаемом recovery новый run также записывает собственный native-sync
receipt и mapping, даже если canonical уже соответствует delta и правок нет.
Не переносить эти поздние этапы в checkbox предшествующего checkpoint.

Проверки изоляции сопоставляют полные пары «маршрут/корень — application» и точное
число вызовов. Для проверки reset учитывать, что asyncio/FastMCP сами изолируют
контекст задач/потоков: наблюдение после завершения dispatch может скрыть отсутствие
reset wrapper. Сохранять реальный MCP-контроль и, где необходимо, проверять тот же
зарегистрированный callback в исходном контексте с чувствительным negative control.

## Дополнение после доставки FIX-04C

FIX-04C опубликована в `2a4c159`. Два native NO-GO сохранены; последний пробел
C2 закрыт отдельным test-only repair и одной явно учтённой дополнительной
проверкой по автономному допуску на локальное исключение. Итоговый review cycle
3 и подтверждение того же thread находятся в manual ledger; native-успех или
обнуление двух обычных review не заявляются. ChangeRail не изменялся.

Доказательства cleanup проверяют каждую операцию отдельно: снимок всех чужих
файлов с байтами, sentinel-ресурсов, fake process identities и сигналов до/после
каждого stop, до следующего stop. Коллективная проверка после остановки всех
приложений может скрыть изменение чужого маркера. Контроль чувствительности
должен падать на немедленном сравнении; его подмена ограничена текущим tmp_path.

При новом планировании declared test selector каждого Cn должен включать
реальные acceptance nodes. Для небольшой семьи удобно держать их в одном
сфокусированном модуле. Сначала окончательные Result/Log, затем retained broad
checks; при отладке использовать точные nodes. Finalize завершает typed proof
и handoff, а не выходит с partial work. Текущая следующая карточка — FIX-05.
