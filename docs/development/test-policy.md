# Проверки qa-mcp

Политика оператора от 2026-09-09: здесь разрабатывается qa-mcp. ChangeRail —
исполняемая зависимость; его исходные тесты, fixtures, evals и разработка остаются
в репозитории ChangeRail. Карточки CHRL-FIX отменены, сохранённая история запусков
не является очередью работ.

## Обычная работа

```sh
uv run pytest --qa-changed --qa-plan
uv run pytest --qa-changed --qa-lane offline --durations=10
uv run pytest --qa-changed --qa-lane integration --durations=10
```

Первый вызов только показывает выбранные проверки. Выбор учитывает изменённые,
добавленные, удалённые, staged/unstaged файлы и обе стороны переименований.
Локальная база — HEAD; для диапазона коммитов задайте `--qa-base <commit>`.
CI передаёт `QA_TEST_BASE`: базу PR/предыдущий push, для release — предыдущий tag.
Чистое дерево без изменений означает отсутствие выбранных проверок, а не полный
прогон. Ошибка определения базы не превращается в успешный пропуск.

Статические Python-импорты, включая относительные импорты и реэкспорты,
связывают тесты с модулями и их зависимостями. Динамические импорты, процессы,
данные и файлы конфигурации дополняются в `config/test-selection.json`.
При добавлении такого потребителя обновляйте карту. Неизвестный изменённый
продуктовый модуль или ресурс требует карты или конкретной проверки; автоматического
fallback на весь набор нет. Это статическая карта зависимостей, не доказательство
полноты покрытия и не результат теста.

Для локального изменения допустим точный файл или node:

```sh
uv run pytest tests/test_config.py -q --durations=10
```

Вызов без селекторов тоже выбирает изменённые модули. Нельзя считать `pytest .`
или название каталога разрешением на полный прогон. В отчёте видны причины
выбора каждого файла. Крупный `mcp_server.py` действительно имеет много
потребителей; пока это один модуль, его изменение может выбирать значительную
часть тестов. Сокращать их без проверки зависимостей нельзя.

## Полная проверка

Полный набор запускается только перед закрытием эпика либо по явному соглашению:

```sh
uv run pytest --qa-full=epic --qa-reason openspec/board/2.todo/EPIC.md --qa-lane offline --cov=qa_mcp
uv run pytest --qa-full=epic --qa-reason openspec/board/2.todo/EPIC.md --qa-lane integration --cov=qa_mcp --cov-append --cov-fail-under=60
```

Вместо `epic` можно указать `approved` с описанием поручения в `--qa-reason`.
Флаг документирует уже полученное разрешение, а не выдаёт его. Полное покрытие
>=60% относится к этому запуску; частичная проверка модулей не обязана покрывать
весь продукт. Обычная финализация карточки, push, PR и release tag полного
прогона не запускают. В CI полный режим доступен отдельным ручным действием.

## Раздельные контуры

| Контур | Содержание | Запуск |
| --- | --- | --- |
| `offline` | Python-логика, подменённые протокол/процессы, небольшие временные файлы | По изменениям |
| `integration` | Настоящий MCP stdio-процесс, свой Xvfb, сборка и проверка артефактов | Отдельно по изменениям |
| `live-linux` | Настоящие Linux TestClient/инфобаза | Только конкретное разрешение и preflight |
| `live-windows` | Настоящие Windows TestClient/инфобаза/desktop | Только конкретное разрешение и preflight |

Каждый pytest-контур печатает `QA LANE START` и `QA LANE END`, время, количество
выбранных случаев, итог и длительность. Будущие живые pytest-проверки размещаются
в `tests/runtime/linux/` и `tests/runtime/windows/`; они получают отдельные
отметки начала/завершения каждого теста. `--qa-live-authorized` обозначает уже
проверенное разрешение; не заменяет preflight и проверку целевой базы.
Пустой живой контур возвращает `runtime_gap` и ненулевой код, а не сертификат
успешной проверки. Сейчас живые сценарии 1С не зарегистрированы как pytest-тесты.

Существующие Windows-native Go-тесты остаются в `host-agent/windows-display-agent/`:
суффикс `_windows_test.go`/build tag отделяет их от переносимой части.
Для изменённого Go-пакета используйте JSON-вывод `go test -json`: события
`run`, `pass`, `fail`, `skip` и elapsed сохраняются целиком. Windows-выполнение
организуется через существующий Linux/Python host-контур с проверенным target;
новый PowerShell/cmd/WSL workflow здесь не вводится. Сценарии, запускающие 1С,
по-прежнему требуют точных platform/infobase inputs, preflight и cleanup evidence.
Успешная Linux-кросс-компиляция не подтверждает Windows-native поведение.

## Инвентаризация и скорость

```sh
uv run pytest --qa-inventory -q > .runtime/qa-test-collection.txt
uv run python -m scripts.qa_test_inventory --collection .runtime/qa-test-collection.txt --output docs/development/test-inventory.json
```

Инвентаризация только собирает тесты и анализирует исходники. Полного выполнения
нет. `test-inventory.md` содержит выводы, JSON — количество случаев, контуры,
входы, хеши файлов и точные совпадения вспомогательных функций.

Измеряйте `--durations=10` на реально затронутых проверках. Повторяющиеся чистые
построители данных можно объединять; изменяемые сессии, ledger, файлы и владение
процессами должны оставаться изолированными. Полная матрица скалярных проверок
обычно принадлежит unit-уровню, а публичному пути — необходимые проверки
прохождения через границу. Уменьшение матрицы требует подтверждения сохранности
контракта, а не произвольного уменьшения числа тестов.
