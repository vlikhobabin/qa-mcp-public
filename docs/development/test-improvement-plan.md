# План улучшения тестов qa-mcp

Дата: 2026-09-10. Статус: T0–T5 выполнены.
[Результаты, измерения и ограничения](test-improvement-results.md).

Основание: [инвентаризация](test-inventory.md),
[машинный снимок](test-inventory.json), [политика проверок](test-policy.md)
и поручение пользователя разобрать слабые проверки, дубли и повторную подготовку.
Это план работ, а не исполняемая карточка или разрешение на публикацию.

## Цель и границы

Сделать продуктовые проверки достовернее и дешевле в сопровождении и исполнении,
сохранив доказательства действующих контрактов qa-mcp. Количество удалённых тестов
и процент ускорения заранее не назначаются: сначала измерение и разбор назначения.

- ChangeRail остаётся исполняемой зависимостью: его код, тесты, fixtures и gates
  в эту работу не входят.
- Обычная проверка охватывает изменённые модули и затронутых потребителей.
  Полный набор — только при закрытии эпика или по отдельному явному соглашению.
  Этот документ сам по себе не создаёт эпик и не разрешает полный прогон.
- Протокол, публичное поведение, lifecycle и политика раскрытия evidence сохраняются.
  Выявленный продуктовый дефект оформляется отдельно от рефакторинга тестов.
- Нет новых PowerShell/cmd/WSL workflows, запуска 1С, Windows-сессий или сборок
  ради подготовки плана. Живые проверки требуют своего поручения и preflight.
- Остановленный FIX-02 не возобновляется. Его сохранённые изменения, установка
  из другой сессии и результаты предыдущей инвентаризации сохраняются.

## Решения после проверки исходников и спецификаций

| Наблюдение | Решение |
| --- | --- |
| Два теста bootstrap вызывают собственный `_select_auto_version()` | Убрать ложное доказательство исполнения; сохранить честные статические проверки поддерживаемой конфигурации |
| Bootstrap ещё упоминается в текущих тестах доставки и шаблоне поддержки платформ | Не считать его устаревшим только по возрасту или языку реализации |
| `_encoded`, `_nested_arrays`, `_tar_bytes` совпадают между файлами | Общие небольшие helpers по предметной области; значения создаются заново |
| Построители runtime target похожи, но различаются policy, identity, endpoint и файлами | Общие данные и явные варианты; свежие context/session/ledger/tmp paths |
| 408 + 116 случаев в двух файлах границы операций | Сначала карта контрактов и затрат; количество не доказывает избыточность |
| Спецификация требует точные 40 URL-комбинаций через MCP и ScenarioRunner | Сохранить все 40; оптимизировать подготовку и общие данные |
| Та же спецификация требует публичные матрицы типов и границ | Не заменять их несколькими smoke-проверками в рамках этого плана |
| Сборки host-agent выполняются дважды для сравнения байтов | Сохранить обе сборки в проверке воспроизводимости |
| Release fixture уже имеет session scope | Не объявлять повторной сборкой каждый использующий её тест |

Контракт публичных матриц:
[`qa-mcp-positive-operation-boundary-public-integration`](../../openspec/specs/qa-mcp-positive-operation-boundary-public-integration/spec.md).
Контракт валидатора:
[`qa-mcp-positive-core-operation-boundary`](../../openspec/specs/qa-mcp-positive-core-operation-boundary/spec.md).
Уменьшение прямо требуемых матриц означало бы отдельное изменение контракта;
оно не включено в план как способ ускорить тесты.

## Порядок работ

| Этап | Приоритет и зависимость | Результат | Размер по сложности |
| --- | --- | --- | --- |
| T0. Карта проверок и исходные измерения | Первый; измерения перед каждым затронутым пакетом | Назначение, выбранные nodes, затраты, сохранённый исходный результат | Небольшой анализ |
| T1. Достоверность проверок доставки | После T0 для этих файлов | Нет тестовой копии алгоритма под видом проверки продукта | Небольшой |
| T2. Чистые helpers | После T0 для потребителей | Убраны три доказанных межфайловых повтора | Небольшой |
| T3. Подготовка контекстов | После T2; последовательная миграция | Меньше повторной подготовки при сохранении изоляции | Средний |
| T4. Матрицы и выбор тестов | После T3 и карты контрактов | Удалены только доказанные излишки либо обоснованно сохранены | Средний, результат зависит от анализа |
| T5. Итоговый отчёт | После выполненных этапов | Сопоставимые измерения, сохранённые обязательства и явные пробелы | Небольшой |

Размер — оценка сложности, не срок и не численный ограничитель. Длительность
будущих прогонов пока неизвестна. Пакеты выполняются последовательно одним
исполнителем; общий helper вводится вместе с его первыми потребителями.

### T0. Зафиксировать назначение и измерить выбранную группу

1. Перед изменением каждого пакета записать точные файлы/nodes, хеши исходников,
   окружение и обоснование выбора. Не использовать общий dirty diff как границу
   пакета: в дереве уже есть изменения других работ.
2. Для каждой изменяемой группы указать владельца поведения, контракт,
   публичный путь, oracle, подготовку ресурсов и зависимости от fixtures.
3. Во время реализации выполнить исходную точечную проверку с `--durations=20`
   и JUnit XML. Различать setup/call/teardown, время всей команды и collection.
   Дорогой build/cache отдельно описать как холодный или повторный.
4. Прежний результат использовать только при совпадающих входах и окружении.
   Сбор всего инвентаря без выполнения не заменяет исходное измерение.

Выход: краткая таблица «проверка → обязательство → владелец → стоимость →
решение». Нельзя выдать оценку полного набора из времени выбранной группы.

### T1. Исправить слабые проверки bootstrap и документации

Файлы: `tests/test_bootstrap_platform_selection.py`,
`tests/test_multi_version_delivery_docs.py`; актуальные ссылки и конфигурационные
источники этих тестов; `config/test-selection.json` только при изменении входов.

1. Удалить использование тестового `_select_auto_version()` как доказательства
   работы bootstrap. По умолчанию сохранить проверки объявленных семейств,
   fallback и необходимых связей конфигурации, назвав их статическими.
2. Проверить текущих потребителей прежде, чем удалять любой legacy-контракт.
   Наличие ссылок сейчас не позволяет объявить bootstrap выведенным из эксплуатации.
3. Сохранить проверку канонического `/mcp`. Для буквальных версий определить,
   являются ли они обязательным примером или текущим списком поддержки. Во втором
   случае использовать существующий канонический источник; не изобретать новый
   реестр и не считать все bundled-семейства автоматически поддержанными live.
4. Не подменять независимый ожидаемый результат вычислением через тот же
   production helper. Условные значения контракта должны иметь независимое основание.

Готово, когда названия и assertions соответствуют классу доказательства,
копия алгоритма не выдаётся за проверку исполнения, а полезные контракты сохранены.
Native-выбор версии остаётся явно непроверенным этим Python-набором. Если для
него требуется реальное доказательство, выделить самостоятельную задачу по
поддерживаемому механизму доставки, не расширяя эту очистку.

Проверка: только два указанных test-файла и потребители реально изменённых входов.
При замене значимого assertion допустим один локальный отрицательный контроль
на тестовых входах; отдельная кампания mutation testing не нужна.

### T2. Объединить чистые helpers

Потребители: два файла `test_positive_*operation_boundary*.py`,
`tests/integration/test_self_hosted_release_scripts.py`,
`tests/test_verify_open_image_archive.py`.

1. Вынести кодирование/вложенные массивы и tar-построитель в раздельные небольшие
   test-support модули. Не помещать архивные и lifecycle-зависимости в общий autouse
   fixture или в тяжёлый package initializer.
2. Сохранить входы, ожидаемые результаты и параметризацию. Одинаковые тела
   вложенных fake/handler функций не переносить без разбора замыканий.
3. Проверить, что изменение helper выбирает всех его потребителей через
   существующий механизм выбора тестов. Исправлять карту только при реальном пробеле.

Готово, когда три повтора имеют по одному владельцу, результаты вызовов свежие,
а прежние проверки потребителей проходят. Для простого переноса helper новые
зеркальные unit-тесты не добавляются. Ускорение не является критерием этого этапа.

Проверка: потребители перенесённых функций. Для tar — использующие его nodes
release-файла и image archive tests; неизменённый тест двойной сборки не нужен.

### T3. Упростить построители контекста без общего изменяемого состояния

Основные файлы: `tests/test_positive_core_operation_boundary.py`,
`tests/test_positive_operation_boundary_integration.py`,
`tests/test_target_bound_evidence_cleanup.py`.
`tests/test_target_bound_lifecycle_admission.py` — дополнительный потребитель:
адаптация только после явного выделения границы сохранённого FIX-02, без изменения
его продуктового payload и без возобновления остановленного запуска.

1. Разделить чистый шаблон profile/observation/env и запись реальных файлов.
   Использовать явные параметры policy, target kind, generation и endpoint.
   Не делать один построитель с неявным исправлением некорректных входов.
2. Чистому валидатору выдавать минимальный корректный контекст. В тестах resolver,
   lifecycle, физических путей и evidence оставить настоящее чтение файлов.
3. Создавать session, ledger, attachment, словари и каталоги заново для каждого
   случая. Не добавлять кэш ApplicationContext и не расширять scope mutable fixture.
4. Мигрировать по одной группе, сравнивая затраты setup и call с T0.

Готово, когда сохранены distinct target/session identity, порядок очистки,
политики sanitized/full_local и поведение некорректных профилей. Существующие
проверки владения и изоляции остаются основным доказательством; новый случай нужен
только для ранее непокрытого риска aliasing, внесённого общим построителем.

Проверка: мигрированная группа и потребители изменённого support-модуля. Если
меняются общие builders обоих boundary-файлов, проверка всех 524 затронутых
случаев оправданна и всё равно не является полным набором qa-mcp.

### T4. Разобрать семантические повторы и слишком широкие зависимости

1. Сопоставить матрицы unit/MCP/BDD с конкретными требованиями. Сохранить все
   40 URL-случаев, предусмотренные публичные границы, отказы до native-вызова,
   provenance, все verdict и operation-local cleanup.
2. Для каждого предлагаемого удаления записать старый node, сохраняемый node,
   одинаковый проверяемый дефект и отсутствие отдельного обязательства/маршрута.
   Сходство данных и общий validator сами по себе недостаточны.
3. Непроверенные default BDD пути из OSS-FIX-09a/b/c не считать покрытыми только
   потому, что тест с injected executor прошёл. Новые регрессии принадлежат
   соответствующим продуктовым карточкам.
4. Если замеры покажут широкое объединение несвязанных потребителей в test-файле,
   разделить файл по поведению и обновить imports/selection. Не выключать реальные
   зависимости для получения меньшего числа выбранных тестов.
5. Для смешанных delivery-файлов рассмотреть выделение чистых структурных проверок
   из integration в offline. Делать это только при конкретной пользе для выбора
   и отчётности, сохранив реальные subprocess/build случаи отдельно.

Готово, когда каждое удаление имеет проверяемое обоснование и сохранённое покрытие
обязательства. Допустимый результат — не удалить ни одного случая, если повторы
проверяют разные пути или требуются спецификацией. Не объединять десятки случаев
в цикл ради уменьшения счётчика: это ухудшает диагностику без сокращения работы.

Проверка: изменённые группы и collection-план их зависимостей. Тест селектора
нужен при изменении самого механизма или новой формы импортов, а не при каждом
обычном переносе. Новый production-рефакторинг `mcp_server.py` в этот этап не входит.

### T5. Подвести результаты и оставить точную карту остатка

Обновить инвентарь после последнего изменения, используя collection без исполнения.
В отчёте по каждому пакету сохранить:

| Поле | Содержание |
| --- | --- |
| Scope | Файлы/nodes и исходные хеши до/после |
| Назначение | Контракты, исправленные слабые assertions, удалённые повторы |
| Результат | Passed/failed/skipped, причины skip, фактическое число случаев |
| Время | Длительность команды, setup/call/teardown, условия кэша |
| Сравнение | Одинаковая группа до/после либо явная пометка, что состав изменился |
| Остаток | Непроверенное native-поведение, данные corpus, отложенные решения |

Локальные логи и XML: `.runtime/test-improvement/<package>/<attempt>/`;
сохранять неудачные попытки. В Git — только краткий безопасный итог.
Один исходный и один итоговый замер группы достаточны для первого сравнения;
повторять только при изменениях, сбое или конкретной неоднозначности результата.
Единичный замер не доказывает устойчивое процентное ускорение.

Windows-only Go tests классифицировать отдельно от live 1С при последующей работе
с host-agent. Уже известные 34 Windows-only функции нельзя считать 34 запусками 1С.
Ни cross-build, ни skip, ни отсутствие зарегистрированных live pytest не являются
доказательством native-поведения. Живой запуск сохраняет начало/конец, target,
preflight, результат и cleanup по существующей политике.

## Что отложено

- Декомпозиция production `mcp_server.py`: только вместе с соответствующей
  продуктовой задачей, если стоимость широкого выбора подтверждается измерениями.
- Новый Windows/bootstrap test harness и расширение live 1С покрытия.
- Глобальное распараллеливание pytest, общий mutable cache, автоматическая
  mutation-testing кампания и новая система бенчмарков.
- Произвольная квота удалений, ослабление обязательных матриц и чистка всей
  исторической документации.

## Переход к исполнению

Первый пакет — T0 для двух delivery-файлов и T1. Он исправляет достоверность
доказательств и не требует переработки runtime. Затем T2, T3 и обусловленный
измерениями T4; T5 фиксирует фактический итог.

Если работа оформляется через доску, готовить по одной обычной `openspec-v1`
карточке на самостоятельный инвариант и один связанный change. Этот план служит
источником scope и критериев, а не заменяет native admission. Не продвигать
карточки и не запускать delivery на основании одного планирования.

Первоначально документ был подготовлен без реализации. После поручения выполнить
T0–T5 этапы завершены; результаты и точечные проверки зафиксированы в отдельном
[отчёте](test-improvement-results.md). Полный набор, live-проверки и ChangeRail
не запускались; публикация не выполнялась. Дополнительный lifecycle-построитель
FIX-02 сохранён, обязательные матрицы оставлены по результатам T4.

- [x] T0 — исходное состояние и выбранные измерения.
- [x] T1 — достоверность bootstrap/docs assertions.
- [x] T2 — общие чистые helpers и проверка потребителей.
- [x] T3 — свежие profile/env данные и корректная подготовка cleanup.
- [x] T4 — карта обязательств и разделение 11 offline случаев.
- [x] T5 — обновлённый инвентарь и итоговый отчёт.
