# Методика дальнейшего исследования

## Базовая стратегия

Оптимальный следующий подход - гибридный:

- точечный replay для новых или непонятных семейств кадров;
- массовый corpus run для построения карты команд, свойств и ответов;
- обязательная нормализация динамических полей перед сравнением.

Текущая инкрементальная методика уже доказала session bootstrap и позволила
получить первый Python-manager read-only результат. Ее не нужно выбрасывать.
Но теперь нужна статистическая ширина: больше команд, типов элементов,
ответов, ошибок и повторных прогонов.

## Почему не один большой сценарий

Один большой эталонный сценарий полезен только после появления маркеров и
автоматической сегментации. Без этого он смешивает:

- технические refresh-запросы;
- полезные запросы к элементам;
- фоновые события формы;
- повторы из-за ожиданий;
- ошибки и recovery-поведение.

Лучше строить корпус как набор коротких сценариев. Каждый сценарий должен
проверять одну группу свойств или одну команду на известной форме.

## Предлагаемая матрица evidence

Для каждого исследуемого действия хранить строку в нормализованной таблице:

| Поле | Назначение |
| --- | --- |
| `case_id` | Стабильный идентификатор кейса. |
| `scenario` | Имя feature/scenario или runner step. |
| `ui_target` | Форма и элемент, если применимо. |
| `api_call` | Vanessa step/API operation или будущий Python call. |
| `expected_state` | Короткое ожидаемое состояние UI. |
| `frame_range` | Номера кадров capture, которые относятся к операции. |
| `request_len` | Длина request body. |
| `response_len` | Длина response body. |
| `normalized_hash` | Hash после удаления ACK GUID, sequence, nonce и live GUID. |
| `operation_token` | Token/command bytes, если выделены. |
| `response_markers` | Строки, GUID, числовые поля, найденные в ответе. |
| `replay_status` | Accepted, rejected, partial, timeout. |
| `notes` | Гипотеза или ограничение. |

## Порядок добавления корпуса

1. Read-only свойства активного окна и формы.
2. Read-only свойства разных типов элементов: надпись, поле ввода, кнопка,
   таблица, диаграмма, командная панель.
3. Навигация между формами и несколькими окнами.
4. Безопасные действия без изменения бизнес-данных: активизация окна, фокус,
   раскрытие меню, переключение вкладок.
5. Мутации на демо-объектах: ввод текста, выбор значения, нажатие кнопки.
6. Negative cases: несуществующий элемент, закрытая форма, timeout, disabled
   element.

## Размер прогонов: пилот, затем батч

Пилоты по 1-3 строки оправданы только для нового класса риска: первый
safe-action, первая мутация, первый диалог, первая реальная форма. Пилот
доказывает схему: manifest -> live preflight -> capture -> изоляция кадров ->
proof -> компактная публикация.

После того как схема класса риска доказана хотя бы одним пилотом, следующие
карточки этого класса планируются как батчи `30-50` manifest-строк за один
capture-прогон. Конвейер manifest-driven, поэтому стоимость батча растет
медленнее, чем стоимость новых одиночных карточек. Поштучные прогоны после
доказанного пилота допустимы только для расследования регрессий, блокеров или
спорных строк.

Прогресс покрытия измеряется не качественной оценкой, а отчетом
`docs/protocol-research/coverage-report.md`, который генерируется
`tools/protocol-research/coverage_report.py` из API-инвентаря и кураторской
карты `case-api-map.json`. Перед любым live-прогоном выполняется
`scripts\preflight-live-runtime.ps1`; провал preflight означает runtime gap до
старта 1C-процессов, а не посреди карточки.

## Правило фиксации нового знания

Новое утверждение о протоколе считается рабочим только если есть:

- capture с исходной операцией;
- нормализованное сравнение с похожими операциями;
- указанные динамические поля;
- replay или Python-manager probe, который подтверждает применимость;
- короткий документ или JSON evidence под `docs/protocol-research/evidence/`.

Семантические и support-источники (`help-mcp`, `meta-mcp`, `config-mcp`,
`bsl-mcp`, `admin-mcp`, `live-mcp`) можно использовать для выбора кейсов,
подписи строк корпуса, controlled authoring, diagnostics и read-only
side-channel проверок, но они не заменяют wire evidence. Если для строки корпуса
есть семантическая карта, она должна ссылаться на первичное evidence с кадрами,
hash и replay/probe status. Неполные или отсутствующие metadata/form-element
связи фиксируются как `partial` или `unresolved`, а не скрываются. Упоминания
`edt-mcp` допустимы только в исторических evidence/roadmap записях.
