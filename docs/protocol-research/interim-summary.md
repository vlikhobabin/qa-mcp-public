## Что уже сделано

Исследование прошло стадию простого пассивного sniffing и перешло к
управляемому воспроизведению. Сейчас у нас есть:

- Windows runtime-обвязка для запуска TestClient, TCP-прокси, Vanessa-сценария
  и сохранения логов в `runtime/protocol-research/captures/<timestamp>/`.
- Доказанный базовый capture `20260602-084433`: 106 manager-to-client chunks и
  107 client-to-manager chunks.
- Разобранная начальная часть сессии: TestClient preface `53 f5 c6 1a 7b`,
  live ACK GUID после третьего кадра, правила подстановки ACK GUID в следующие
  manager frames, sequence и nonce.
- Генератор шаблонов manager frames с динамическими полями:
  `ack_guid`, `sequence`, `nonce`, `managed_form_guid_ascii` и
  `managed_form_guid_utf16le`.
- Python-клиент, который уже может выполнять узкие read-only запросы без
  запуска 1C в режиме TestManager:
  `initial-ui`, `active-form-context`, `form-summary`,
  `form-element-details`.
- Доказанный короткий replay schedule `1..17,101..106`, который принимает
  TestClient и возвращает сведения по двум элементам формы без прокрутки всей
  серии `31..100`.
- Классификация request series:
  - frames `18..30`: повторяемые `managed_form_ref_request`;
  - frames `101..106`: element-detail requests с operation token на offset 51
    и разными semantic labels для трех операций.

Практический результат: уже можно говорить не только о логировании протокола,
а о первом рабочем Python TestManager для ограниченного read-only сценария.

## Насколько далеко до полного описания

До полного описания всего протокола еще далеко. Мы понимаем транспортный вход в
сессию и несколько семейств read-only UI-запросов, но пока почти не покрыты:

- действия пользователя: click, input, select, command execution;
- ожидания, события формы, фоновые изменения, async-переходы;
- ошибки, таймауты, negative responses и восстановление сессии;
- многооконные сценарии и смена активной формы;
- разные типы элементов, таблицы, команды формы, панели, меню;
- различия платформенных версий, тонкий/толстый клиент, разные конфигурации;
- семантическая структура бинарных ответов глубже уровня строк, GUID и
  размеров.

Оценка прогресса качественная, не метрическая:

- session bootstrap для наблюдаемой версии платформы: уже хорошо изучен;
- narrow read-only manager: реализуем и воспроизводим;
- практическая read-only поверхность Vanessa UI: покрыта частично;
- полный протокол TestManager/TestClient: большая часть еще не описана.

Если переводить это в грубую инженерную оценку, мы прошли наиболее рискованную
первую развилку: стало понятно, что Python-менеджер возможен. Но до
самостоятельной замены Vanessa manager для широкого набора UI-операций нужна
системная карта команд и ответов.

## Оценка подхода

Текущий поэтапный подход был рационален: сначала нужно было понять handshake,
динамические поля, replayability и минимальный живой запрос. Большой
эталонный сценарий до этого дал бы много байтов, но мало доказуемых
соответствий.

Следующий этап стоит оптимизировать гибридно:

- оставить инкрементальный replay для неизвестных frame families и опасных
  write/action-команд;
- добавить эталонный corpus runner, который массово прогоняет команды и
  свойства, но с разбиением на короткие маркированные сценарии;
- для каждого шага сохранять таблицу соответствия: Vanessa/API call,
  ожидаемое UI-состояние, диапазон кадров, normalized request hash,
  operation token, строки/идентификаторы в ответе, replay result.

Иными словами, массовый прогон нужен, но не как один слепой огромный скрипт.
Лучше сделать корпус маленьких сценариев с явными маркерами и автоматической
сводной таблицей.

## Ближайшие вехи

1. Оформить `qa-mcp` как отдельный репозиторий и перенести туда исследование.
2. Стабилизировать `tools/protocol-research` как повторяемый lab toolkit.
3. Спроектировать `reference-corpus`: список read-only свойств и UI-команд по
   типам элементов.
4. Добавить нормализованную evidence database: frame family, hash, token,
   semantic label, request/response strings, replay status.
5. Перенести проверенные части Python manager из `tools/` в `src/qa_mcp/`.
6. После read-only покрытия перейти к безопасным action-командам на демо-базе.
